Fungování

  • Unity je native engine s C# wrapperem. API UnityEngine.* je tenká managed fasáda nad nativními objekty.
  • Většina práce: transformace, kolize, vykreslování: probíhá v C++.
  • C# řídí logiku a orchestraci, ne vnitřní smyčky enginu.
  • Interop: režie na hranici světů

Důsledek: každé volání API může znamenat přechod managed → native. Nativní objekty mají vlastní životní cyklus, který managed GC neřídí. Odtud pramení většina „divných“ chování Unity.

Tohle je základní mentální model celé přednášky. Unity není čistě C# engine: C# je řídící vrstva nad C++ jádrem. Když voláte transform.position, neděje se to v C#, ale v nativním objektu. To vysvětluje, proč existují dvě úrovně života objektů, proč je serializace potřeba a proč je volba backendu důležitá.
Architektura • Objektový model

GameObject–Component model

Scene
├─ GameObject „Player“
├─ Transform
├─ Rigidbody
└─ PlayerController (MonoBehaviour)
└─ GameObject „Main Camera“
├─ Transform
└─ Camera

Skládání místo dědičnosti

  • GameObject je kontejner; chování dodávají komponenty.
  • MonoBehaviour je managed komponenta; Transform, Rigidbody a Camera jsou nativní komponenty.
  • Skripty dostávají vlastní Update / FixedUpdate callbacky.

Dvojí identita objektu

  • Každý UnityEngine.Object má nativní protějšek a managed wrapper.
  • Object.Destroy zničí nativní objekt; wrapper žije dál → nastav null.
  • Proto Unity přepisuje == a !=: zničený objekt se porovná jako null.
GameObject–Component je známý koncept, ale tady ho potřebujeme kvůli dualitě. Když v Inspectoru přetáhnete komponentu, pracujete s nativním objektem. Když na něj v C# držíte referenci, držíte managed wrapper. Tenhle rozdíl se vrátí u serializace i u GC.
Architektura • Herní smyčka

Player loop a životní cyklus

Init Awake → OnEnable → Start (Start jen před prvním Update)
Physics FixedUpdate v pevném intervalu Time.fixedDeltaTime, poté kolizní a trigger callbacky
Update Input a herní logika: jednou za snímek
Coroutines Pokračování po dokončení Update; WaitForFixedUpdate po fyzice
LateUpdate Dokončení logiky: typicky pohyb kamery
Rendering Culling → draw → post-processing
Teardown OnDisable → OnDestroy → OnApplicationQuit

Co z toho plyne

  • FixedUpdate nezávisí na FPS: fyzika má vlastní čas.
  • Update: Time.deltaTime
  • Pořadí mezi objekty není deterministické; lze vynutit Script Execution Order.
  • Rendering callbacky typu OnPreCull patří built-in pipeline; URP a HDRP používají RenderPipeline hooky.

Pozor: Awake a OnEnable jsou garantované v rámci jednoho objektu. Mezi objekty pořadí garantované není.

Studenti často řeší, proč se jim něco volá dřív než něco jiného. Odpověď je player loop. Zdůrazněte dvě věci: fyzika běží ve fixním kroku, a pořadí mezi různými objekty není garantované. Zároveň upozorněte, že část render callbacků je legacy: v URP a HDRP se používá jiný mechanismus.

Roslyn a assembly

  • Roslyn přeloží skripty do managed assemblies (.dll) obsahujících CIL/MSIL: platformově nezávislý mezikód.
  • Assembly je kompilační jednotka; v Unity ji řídí Assembly Definitions.
  • Assembly Definition: izolovaná rekompilace
  • Unity kompiluje i balíčky a pluginy; pořadí určují závislosti asmdef.

Backend rozhoduje, co bude dál

  • Mono: assembly se načtou do runtime a zkompilují JIT za běhu.
  • IL2CPP: assembly se převedou do C++ a zkompilují AOT při buildu.
  • Stejný C# kód, dva velmi odlišné výsledky.
  • Výstup: JIT runtime / nativní binárka
Tady se láme celá druhá kapitola. C# není v buildu přímo: vždy existuje mezikód. Backend určuje, jestli se mezikód zpracuje za běhu, nebo předem. To ovlivní rychlost, velikost, platformy i to, jestli funguje dynamické generování kódu.
.NET • Skriptovací backendy

Dva skriptovací backendy

Mono

  • Historický backend Unity.
  • JIT: kompiluje kód na vyžádání za běhu.
  • Runtime: součást buildu
  • Používá se v Editoru; dostupný na desktopu a části mobilních platforem.
  • Umožňuje dynamické generování kódu a rychlejší iteraci.

IL2CPP

  • Unity vlastní backend.
  • AOT: celá aplikace se kompiluje před spuštěním.
  • Výsledek: nativní binárka
  • Vyžadován tam, kde není povolen JIT: iOS, konzole, WebGL.
  • Bez JIT: žádný dynamický kód
  • Převádí CIL do C++ a používá nativní kompilátor platformy.

Kde to přepnout: Edit > Project Settings > Player > Other Settings > Scripting Backend. Nastavení je per-platform.

Backend není lepší nebo horší: je to volba podle platformy a potřeb. Editor vždy běží na Mono, takže vývoj je rychlý. Do buildu se ale dostane to, co zvolíte. Pro iOS nebo konzole nemáte na výběr.
.NET • Mono

Mono a JIT kompilace

Princip

  • Managed assembly se načte do Mono runtime.
  • Metody se kompilují just-in-time při prvním volání.
  • První volání: pomalejší
  • Strojový kód specifický pro platformu vzniká až na cílovém zařízení.
  • Editor používá Mono vždy: díky tomu funguje rychlý Enter Play Mode a hot reload.

Plusy

  • Rychlý build, menší binárka, rychlá iterace.
  • Dynamické generování kódu a plná reflexe.
  • Snadné ladění v Editoru.

Mínusy

  • JIT není povolen na iOS, konzolích a WebGL.
  • Pomalejší start a méně předvídatelný výkon.
  • Runtime musí být součástí buildu.
  • Release: vhodnější IL2CPP
JIT znamená „až za běhu“. Výhodou je flexibilita a rychlý vývoj, nevýhodou závislost na runtime a horší predikovatelnost výkonu. Pro prototypy a desktop je Mono pohodlná volba.
.NET • IL2CPP

IL2CPP a AOT pipeline

1
Roslyn zkompiluje C# do managed assemblies (.dll).
2
Unity aplikuje managed bytecode stripping.
3
IL2CPP převede všechny managed assemblies do standardního C++.
4
Nativní C++ kompilátor platformy zkompiluje vygenerovaný kód.
5
Unity vytvoří spustitelný soubor nebo DLL podle cílové platformy.

Co z toho plyne

  • Běh je nativní: žádný JIT, žádné dynamické generování kódu.
  • Runtime: žádný .NET/JIT
  • Širší podpora platforem: iOS, konzole, WebGL.
  • Vyšší výkon a obtížnější reverzní inženýrství.
  • Delší build, větší binárka; generika mohou build dál nafouknout.

IL2CPP je kompilátor, ne interpret. Výsledkem je běžný C++ kód zkompilovaný nativním toolchainem.

IL2CPP je kompilátor, ne interpret. Klíčové je, že výsledkem je běžný C++ kód zkompilovaný nativním toolchainem. To přináší výkon a podporu platforem, ale bere dynamické funkce .NET. Když používáte knihovnu, která generuje kód za běhu, v IL2CPP nepojede.

.NET • Stripping

Managed code stripping

Princip

  • Unity prochází assemblies a odstraňuje nepoužitý kód.
  • Analýza: statické skenování assemblies
  • Cíl: menší build a méně kódu k načtení.
  • U Mono je stripping ve výchozím stavu vypnutý.
  • U IL2CPP ho nelze vypnout.

Úrovně a rizika

  • Řízeno přes Managed Stripping Level: Player > Other Settings.
  • Vyšší úroveň = agresivnější odstranění = menší build.
  • Riziko: odstranění kódu volaného pouze přes reflexi nebo generování za běhu.
  • Řešení: anotace [Preserve], link.xml, správné asmdef závislosti.

Stripping je optimalizace velikosti, ne výkonu. Neplatíte za ni za běhu, ale při buildu.

Stripping je typický zdroj „works in Editor, fails in build“. Editor má Mono stripping obvykle vypnutý, IL2CPP ho má vždy. Pokud používáte serializaci přes reflexi nebo DI framework, musíte kód označit jako preservovaný.
.NET • Profily

API Compatibility Level

.NET Standard

  • Výchozí a doporučená volba pro nové projekty.
  • Menší API surface → menší build.
  • Lepší cross-platform kompatibilita.
  • Všechny .NET runtimes implementují .NET Standard.

.NET Framework

  • Širší API, ale platformově vázanější.
  • Vhodné pro legacy kód a knihovny, které standard nepodporují.
  • Větší binárka a větší riziko nekompatibility.

Nastavení: Project Settings > Player > Other Settings > Api Compatibility Level. Ne všechny systémové knihovny jsou podporované (např. System.Drawing); výkon a alokace se mezi verzemi Unity mohou měnit.

Studenti často přepnou na .NET Framework, protože jim chybí nějaká třída. To je někdy nutné, ale vždy za cenu přenositelnosti a velikosti. Pro nový projekt zůstaňte na .NET Standard, dokud vás něco konkrétního donutí jinak.
.NET • Paměť

Garbage collector

Boehm GC

  • Unity používá Boehm GC pro Mono i IL2CPP.
  • Spravuje managed haldu: třídy, stringy, pole, boxované hodnoty.
  • Nativní objekty (UnityEngine.Object) GC neřídí.

Incremental vs. stop-the-world

  • Výchozí je incremental GC: práce rozložená do více snímků.
  • Lze přepnout na stop-the-world: kratší, ale citelné záseky.
  • Nastavení: Player > Other Settings > Use incremental GC.
  • Scripting.GarbageCollector umí GC úplně vypnout: jen velmi opatrně.

Praxe

  • Měřte alokace v Profileru.
  • Vyhněte se alokacím ve Update: stringy, LINQ, foreach přes nové kolekce.
  • Cíl: žádné alokace ve frame loopu.
  • Nástroje: pooling, StringBuilder, for
  • Nativní paměť se uvolňuje přes Destroy, ne GC.

Vypnutí GC není optimalizace. Je to poslední záchranná brzda.

GC je nejčastější příčina mikrozáseků. Incremental GC je kompromis: nerozloží práci do jednoho framu, ale může běžet častěji. Vysvětlete, že optimalizace začíná měřením, ne vypnutím GC. Zároveň připomeňte, že nativní objekty se uvolňují přes Destroy, ne garbage collectorem.
.NET • Nativní objekty

UnityEngine.Object: dva životy objektu

1
C# wrapper drží referenci na nativní objekt v C++.
2
Object.Destroy() zničí nativní objekt. Managed wrapper zůstává.
3
GC uvolní wrapper až po ztrátě poslední reference.
!
Zničený MonoBehaviour nebo ScriptableObject se nikdy automaticky neobnoví.

Přepsané operátory

  • == a != neporovnávají jen managed reference. Ptají se i na nativní objekt.
  • Zničený objekt se proto rovná null, i když wrapper existuje.
  • WeakReference nad UnityEngine.Object není podporován.
  • DestroyImmediate slouží pro Editor; v runtime se nepoužívá.
  • Po Destroy: reference = null

Nikdy nekontrolujte obj == null přes ReferenceEquals: v Unity to není totéž.

Tohle je klasika, na kterou narazí každý. Vysvětlete, že == null v Unity není jen porovnání referencí, ale dotaz na nativní objekt. Proto může být objekt nenullový z pohledu C# a přesto se chovat jako null. A proto nelze použít WeakReference.
.NET • Omezení runtimu

Reflexe, vlákna a async/await

Reflexe

  • Unity cachuje System.Reflection objekty a neuvolňuje je GC.
  • Časté skenování (Assembly.GetTypes, Type.GetMethods) vytváří GC overhead.
  • Řešení: předpočítat v Editoru, serializovat nebo generovat kód.

Vlákna

  • Unity API není thread-safe.
  • Většina volání musí běžet na hlavním vlákně.
  • V development buildu Unity vyhodí výjimku při volání API z jiného vlákna.

async/await

  • Unity přepisuje SynchronizationContext na UnitySynchronizationContext.
  • await se vrací na hlavní vlákno; Task.Run běží na pozadí.
  • Task.Run: mimo Unity API
  • Tasky nejsou zastaveny po ukončení Play mode: odhlaste se přes EditorApplication.playModeStateChanged.

Doporučení: pro paralelní práci s daty používejte Job System a Burst, ne ruční vlákna.

async/await je užitečný, ale v Unity platí tři pravidla: hlavní vlákno, hlavní vlákno, hlavní vlákno. Job System je bezpečnější cesta pro výpočty nad daty. U reflexe zdůrazněte, že cache není GC: takže i „jen čtení“ může dlouhodobě růst.
Serializace • Koncept

Serializace: co to je a proč existuje

Serializace je automatický proces převodu datových struktur nebo stavu GameObjectu do formátu, který Unity umí uložit a později rekonstruovat.

Scény a prefaby

  • Uložený stav komponent a hierarchie.
  • Reference mezi objekty.
  • Prefab je serializovaná šablona; instance přebírá uložené hodnoty.

Assety a Inspector

  • ScriptableObject, materiály, animace, importní nastavení.
  • Změna v Inspectoru se zapíše do serializovaných polí.

Editor a build

  • Undo/Redo, domain reload po rekompilaci, přechod do Play mode.
  • Domain reload: managed stav se ztrácí
  • Build ukládá serializovaná data do assetů a scén.

Serializace je most mezi managed světem a trvalým úložištěm. Vše, co má přežít reload, musí být serializované.

Studenti berou Inspector jako samozřejmost. Tady je potřeba ukázat, že za ním stojí serializace. Když položíte do třídy pole, Unity ho musí umět uložit: jinak se hodnota ztratí při každém reloadu. To je důvod, proč existují pravidla na dalším slidu.
Serializace • Pravidla

Která pole se serializují

Pole musí splnit Příklad
Je public, nebo má [SerializeField] public int health;
Není static, const ani readonly readonly float speed; ×
Typ je serializovatelný Vector3, List<T>, [Serializable] třída

Properties se standardně neserializují.

Projde
public class Enemy : MonoBehaviour
{
    public int health;                  // public
    [SerializeField] private int armor; // private + atribut
    [SerializeField] private Weapon weapon;
}
Neprojde
public static int score;        // static
private const int MaxHp = 100;  // const
private readonly float speed;   // readonly
private int secret;             // private bez atributu
Tohle je nejpraktičtější slide celé kapitoly. Řekněte studentům, ať si zapamatují tři podmínky. Čtvrtá věc: properties: je častý omyl. public int Health { get; set; } se v Inspectoru neobjeví.

Serializace • Vlastní typy

Vlastní třídy: inline vs. SerializeReference

Vlastnost Inline (výchozí) [SerializeReference]
Uložení kopie hodnoty do vlastníka managed reference
Sdílení instance ne: vznikne duplikát ano
null hodnota ne ano
Cyklické grafy ne ano
Polymorfismus ne ano
Režie nižší vyšší
Dvě podoby pole
[Serializable]
public class Weapon { public int damage; }

public class Enemy : MonoBehaviour
{
    // inline kopie
    [SerializeField] private Weapon weapon;
    // polymorfní reference
    [SerializeReference] private AIState state;
}

Třída musí mít [Serializable] a nesmí být statická. Pro běžná data preferujte inline; [SerializeReference] používejte jen když potřebujete null, sdílení, cykly nebo polymorfismus.

Tady je důležité pochopit rozdíl. Inline znamená, že když stejný objekt přiřadíte do dvou polí, Unity uloží dvě kopie. SerializeReference udrží jednu instanci a referenci. Za to platíte režií a složitějším chováním v Inspectoru.
Serializace • Slovníky

ISerializationCallbackReceiver

Problém: Dictionary<K,V> Unity neserializuje.

Řešení: dva callbacky

  • OnBeforeSerialize(): převést runtime strukturu na Unity-friendly data (paralelní pole).
  • OnAfterDeserialize(): znovu sestavit slovník.
  • Dictionary: 2 paralelní pole
  • Callback běží při ukládání i načítání: neprovádějte v něm drahé operace.

Stejný vzor funguje pro jakoukoli strukturu, kterou Unity neumí uložit: převést na pole a zpět.

ItemDatabase.cs
[Serializable]
public class ItemDatabase : ISerializationCallbackReceiver
{
    private Dictionary<string, Item> _items = new();

    [SerializeField] private List<string> _keys = new();
    [SerializeField] private List<Item> _values = new();

    public void OnBeforeSerialize()
    {
        _keys.Clear();
        _values.Clear();
        foreach (var pair in _items)
        {
            _keys.Add(pair.Key);
            _values.Add(pair.Value);
        }
    }

    public void OnAfterDeserialize()
    {
        _items.Clear();
        for (int i = 0; i < _keys.Count; i++)
            _items[_keys[i]] = _values[i];
    }
}
Tohle je vzor, který studenti ocení v praxi. Ukázka je záměrně krátká: dvě paralelní pole a dvě metody. Zdůrazněte, že slovník zůstává privátní a Inspector vidí jen pole.

Serializace • Praxe

Best practices serializace

1. Jen nutné minimum

Méně dat znamená menší build a méně chyb. Serializujte jen to, co má přežít reload.

2. Žádná duplicitní data

Neukládejte cached ani odvozené hodnoty. Přepočítejte je při načtení.

3. Pozor na rekurzi

Vyhněte se rekurzivním strukturám, pokud nejsou potomky UnityEngine.Object nebo nepoužívají [SerializeReference].

4. Inline jako default

[SerializeReference] jen pro null, sdílení, cykly nebo polymorfismus.

Serializace je kontrakt s Editorem. Když ho porušíte, hodnoty se tiše ztratí: žádná výjimka, jen prázdné pole.

Pravidla jsou krátká, ale řeší většinu problémů. Zdůrazněte poslední větu: serializace selhává tiše. Proto je dobré mít vlastní validaci a testy, které po reloadu ověří, že data zůstala.
Render pipelines • Koncept

Co je render pipeline

Render pipeline přebírá objekty ve scéně a zobrazuje je na obrazovce. Opakuje se při každém snímku, který Unity vygeneruje.

1. Cullingodstraní objekty mimo kameru a zakryté objekty
→
2. Renderingvykreslí objekty se správným osvětlením do bufferů
→
3. Post-processingupraví buffery do finálního obrazu

Rendering path

Série operací, které kreslí a osvětlují objekty, jež kamera vidí.

  • Forward: per-object
  • Deferred: G-buffer
  • Forward+: per-tile (URP)

Kdo pipeline řídí

Built-in je pevná pipeline ovlivnitelná command buffery. URP a HDRP jsou postavené na SRP: culling, rendering i post-processing jsou C# kód.

Začněte jednoduchou definicí. Culling, rendering, post-processing: tyto tři kroky platí pro všechny pipeline v Unity 6.6. Nově zdůrazněte, že pipeline není totéž co rendering path: pipeline je celý systém, rendering path je způsob, jakým se v něm kreslí a osvětluje geometrie.
Render pipelines • Přehled

Tři render pipelines v Unity 6.6

Unity 6.6: Built-In Render Pipeline je deprecated. Bude obsolete v budoucím vydání; bug-fixy a údržba potrvají po celý Unity 6.7 LTS lifecycle. Nové projekty startujte na URP nebo HDRP.

URP

  • Předpřipravená SRP od Unity.
  • Škálovatelná grafika na všech Unity platformách: mobil až high-end konzole a PC.
  • Shader Graph, VFX Graph, SRP Batcher.
  • Rozumný default pro nové projekty.

HDRP

  • Předpřipravená SRP pro high-end platformy.
  • Fyzikálně založené osvětlení a materiály, forward i deferred.
  • AAA hry, automotive, architektura.
  • 3D projekty; náročné na hardware.
  • Platformy: PC, konzole, Switch 2

Built-in deprecated

  • Obecná pipeline s omezeným přizpůsobením.
  • Není postavená na SRP.
  • Jen pro legacy projekty, které se dosud nepodařilo migrovat.
  • Podpora končí s Unity 6.7 LTS.

URP a HDRP nelze v jednom projektu používat současně. Oba jsou SRP, ale mají odlišné render paths a light modely.

Tady je hlavní změna oproti starší verzi přednášky: Built-in už není rovnocenná třetí volba. Pro nový projekt je rozumný default URP; HDRP je specialista na high-end. Deprecation banner čtěte doslova: podpora končí s Unity 6.7 LTS, ne dřív, ale nový projekt na Built-in nezačínejte.
Render pipelines • Built-in

Built-In Render Pipeline (deprecated)

Status

  • Deprecated v Unity 6.6.
  • Bude obsolete v budoucím vydání.
  • Bug-fixy a údržba po celý Unity 6.7 LTS lifecycle.
  • Pro nové projekty se nedoporučuje.

Charakteristika

  • Starší pipeline Unity; není založená na SRP.
  • Rendering paths: Forward, Deferred, Legacy Vertex Lit.
  • Přizpůsobení přes command buffers a callbacky.
  • Většina kódu je C++ a privátní; přístup je nutné zakoupit.

Migrace

  • Built-in → URP: URP Render Pipeline Converter; převod materiálů a shaderů.
  • Built-in → HDRP: HDRP Pipeline Wizard; náročnější, často ruční přetvoření materiálů.
  • Manuální úpravy custom shaderů a render callbacků.

Kdy ho použít: pouze existující legacy projekt, který zatím nelze migrovat. Migraci naplánujte před koncem Unity 6.7 LTS.

Built-in není špatný, je jen na konci životního cyklu. Zdůrazněte, že podpora nekončí okamžitě: Unity 6.7 LTS je poslední LTS, které ho ponese. Pro studenty to znamená jediné: nový projekt v Unity 6.6 startujte na URP nebo HDRP, ne na Built-in.
Render pipelines • URP

Universal Render Pipeline

Co to je

  • Předpřipravená SRP vytvořená Unity.
  • Škálovatelná grafika na všech Unity platformách: mobil, desktop, konzole, VR, WebGL.
  • Optimalizace pro TBDR a untethered VR.
  • Rozumný default pro nové projekty.

Vlastnosti

  • Shader Graph a VFX Graph.
  • SRP Batcher, BatchRendererGroup, Entities (DOTS).
  • GPU Resident Drawer (v URP vypnutý) a GPU occlusion culling.
  • Od URP 17 render graph system pro vlastní passy.

Rendering paths

  • Forward (výchozí): jednoduchý, limity světel na objekt.
  • Deferred / Deferred+: mnoho světel, detailní stíny.
  • Forward+: bez limitu světel na GameObject; světla per-tile.

Kdy ho použít

Cross-platform 2D i 3D, mobil, TBDR hardware, VR, konzole i desktop. Nové projekty, které chtějí rozšiřitelnost a aktivní vývoj.

URP je rozumný default pro nové projekty. „Universal“ neznamená nejnižší kvalita: znamená rozsah platforem. Ukažte tři rendering paths: Forward pro jednoduchost, Forward+ pro mnoho světel bez per-object limitu, Deferred pro mnoho světel a detailní stíny. Zmiňte, že URP 17 přinesl Render Graph a GPU Resident Drawer.
Render pipelines • HDRP

High Definition Render Pipeline

Co to je

  • Předpřipravená SRP pro špičkovou, vysoce věrnou grafiku.
  • Fyzikálně založené osvětlení a materiály.
  • Forward i deferred rendering.
  • Využívá compute shadery; vyžaduje kompatibilní GPU.

Vlastnosti

  • Pokročilé PBR: clear coat, skin, hair, eyes, subsurface scattering, water.
  • Fyzikální jednotky světla, volumetrics, pokročilé stíny.
  • Ray tracing na podporovaném hardware.
  • Render Graph a GPU Resident Drawer (v HDRP zapnutý).

Platformy

  • Desktop (Windows, macOS, Linux), Xbox, PlayStation.
  • Nintendo Switch 2.
  • Ne: původní Switch, iOS, Android, mobilní VR, WebGL.
  • Pouze 3D: bez 2D nástrojů URP.

Kdy ho použít

AAA hry, automotive demos, architektonické vizualizace, fotorealistické scény na výkonném hardware.

HDRP je nejvyšší kvalita za nejvyšší cenu. Nově je dobré zmínit Switch 2: v tabulce podpory Unity 6.6 je HDRP pro Switch 2 dostupné, zatímco původní Switch, mobily a WebGL ne. Pro fotorealistickou scénu na PC nebo konzoli je to správná volba, ale vyžaduje zkušený grafický tým.

Render pipelines • SRP

Architektura SRP

1
RenderPipelineAsset
ScriptableObject: konfigurace + CreatePipeline()
↓ vytváří
2
RenderPipeline Instance
runtime objekt s metodou Render()
↓ každý frame
3
ScriptableRenderContext
fronta příkazů → low-level graphics → graphics API

Proč na tom záleží

  • SRP je tenká C# API vrstva pro plánování a konfiguraci rendering příkazů.
  • URP, HDRP i vlastní pipeline jsou postavené na SRP.
  • Render Graph je vyšší API v SRP Core pro správu passů a zdrojů; URP 17 ho používá.

SRP běží na hlavním vlákně. Příkazy se zapisují do ScriptableRenderContext a odesílají metodou Submit().

Tohle je architektonické jádro grafické části. Asset je konfigurace, instance je běžící pipeline, Render je vstupní bod, context je fronta příkazů. Když to student pochopí, přestane být URP černá skříňka. Render Graph je nadstavba, ne náhrada SRP.
Render pipelines • Vlastní pipeline

Vlastní SRP

Postup

  • Přidat SRP Core package; volitelně URP/HDRP jako referenci.
  • Vytvořit třídu dědící z RenderPipelineAsset, přepsat CreatePipeline().
  • Vytvořit třídu dědící z RenderPipeline, implementovat Render(...).
  • Naplánovat culling, draw a post-processing; použít ScriptableRenderContext, nebo Render Graph.
  • Asset přiřadit v Project Settings > Graphics.

Pro produkci je lepší vycházet z URP/HDRP. Pro vlastní passy v URP 17+ používejte Render Graph.

MyPipeline.cs
public class MyPipelineAsset : RenderPipelineAsset
{
    protected override RenderPipeline CreatePipeline()
        => new MyPipeline();
}

public class MyPipeline : RenderPipeline
{
    protected override void Render(
        ScriptableRenderContext context, Camera[] cameras)
    {
        foreach (var camera in cameras)
        {
            context.Cull(...);
            context.SetupCameraProperties(camera);
            context.DrawRenderers(...);
            context.Submit();
        }
    }
}
Ukázka je záměrně minimální: chybí jí spousta věcí, které produkční pipeline potřebuje. Cílem je ukázat tvar API: asset, instance, Render, context. Zdůrazněte, že vlastní SRP je pokročilá disciplína a že v Unity 6 je doporučená cesta pro rozšíření URP Render Graph, ne vlastní pipeline od nuly.

Render pipelines • Rozhodování

Jak vybrat pipeline

1. Cílové platformy

Mobil, VR, WebGL → URP.
High-end PC a konzole → HDRP.
Legacy → Built-in jen dočasně.

2. Vizuální cíl

Stylizovaná grafika a flexibilita → URP.

Shader Graph, VFX Graph a vlastní passy → URP.
Složitější high-end pipeline → HDRP.

Fotorealistický high-end → HDRP.
Legacy → Built-in jen do konce Unity 6.7 LTS.

Závěr • Shrnutí

Shrnutí

1. Native + managed

Unity je native engine s C# fasádou: výkon v C++, logika v C#.

2. Backend podle platformy

Mono/JIT pro iteraci, IL2CPP/AOT pro iOS, konzole a WebGL.

3. AOT mění pravidla

Žádné dynamické generování kódu; pozor na reflexi a stripping.

4. Serializace je kontrakt

Public nebo [SerializeField], podporovaný typ, žádná statická či readonly pole.

5. Serializujte minimum

Žádná duplicitní data, inline jako default, [SerializeReference] jen když je potřeba.

6. Pipeline na začátku

URP jako rozumný default, HDRP pro high-end, Built-in jen jako deprecated legacy do 6.7 LTS.

Architektura Unity není náhoda: každé omezení má důvod v oddělení nativního a managed světa. Kdo to chápe, píše předvídatelnější a rychlejší hry.

Šest bodů, které si mají odnést. Projděte je rychle, bez nových informací. U posledního bodu zdůrazněte deprecaci Built-in pipeline: je to největší změna oproti starším verzím Unity. Pokud zbývá čas, otevřete diskusi o tom, jaké pipeline a backendy používají studenti ve svých projektech.
