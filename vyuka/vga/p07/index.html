Frame buffer (FB)

2D pole pixelů na obrazovce. Po řádcích zleva doprava shora. Proč?

Frame buffer je v paměti grafické karty, přímo z něj vykresluje.

Před hardwarovou akcelerací pouze přímá manipulace programem.

Spotřeba paměti záleží na grafickém režimu / rozlišení, např.:

textový režim 40×25, 1B znak + 1B atributy = 40×25×2 = 2 kB

textový režim 80×25, 1B znak + 1B atributy = 80×25×2 = 4 kB

grafický režim 320×200, černobílý = 320×200/8 = 8 kB

grafický režim 320×200, 256 barev = 320×200×1 = 64 kB

grafický režim 640×480, 256 barev = 640×480×1 = 300 kB

grafický režim 640×480, 16 bitů = 640×480×1 = 600 kB

grafický režim 1024×768, 24 bitů = 1024×726×3 = 2 MB

grafický režim 1920×1080, 24 bitů = 1920×1080×3 = 6 MB

grafický režim 3840×2160, 10b/kanál = 3840×2160×4 = 29 MB

Poznámka GRAFIT: V příkladech PDF jsou početní překlepy: 16 bitů znamená 2 B na pixel, nikoli uvedené ×1; pro 1024×768 se v součinu objevuje 726. U 3840×2160×4 vychází 33 177 600 B = 31,64 MiB, nikoli 29 MB. Model GRAFIT počítá přesné bajty a odděluje MB od MiB. Balení 10bitových kanálů závisí na pixelovém formátu.

FB versus výkon CPU v 80. a 90. letech 20. století

Příklad 1

Rok 1982. Intel 80286, 4 Mhz; roku 1985 vyšla 10MHz verze.

Předpokládejme 5 cyklů na instrukci a tedy 2 MIPS.

Standardní režim VGA, tedy 320×200×256 barev, tedy 64 kB.

Chceme 25 FPS. Musíme protočit 64k×25 = 1.6 MB/s.

Máme něco málo přes 1 instrukci na pixel. A to nepočítáme herní logiku.

Při 10 FPS máme 3 instrukce na pixel… pořád málo prostoru.

Příklad 2

Rok 1989, Intel i486, roku 1992 vyšla 25MHz verze i486SX.

Až 20 MIPS.

Stejné rozlišení, 25 FPS, tedy 1.6 MB/s.

Máme 12 instrukcí na pixel. Už lze i načíst pixel z textury.

Poznámka GRAFIT: Jde o orientační historický model: MIPS a instrukce na pixel nejsou spolehlivým měřítkem konkrétního programu. Nezapočítávají propustnost paměti, cache ani rozdílnou cenu instrukcí.

Paletové efekty

Pokud používám (nejvýše) 256barevný režim, mám obvykle možnost zvolit si přiřazení barev jednotlivým indexům.

Dle standardu VGA je k dispozici 6 bitů na každý ze 3 barevných kanálů, tedy celkem 262144 různých barev.

Převod indexu na barvu provádí grafická karta, tedy barevná paleta ovlivňuje obraz až při zobrazování.

Paletu můžeme v průběhu kdykoliv jednoduše měnit (768 malých čísel). Možné efekty:

Postupné ztmavování / rozsvěcení obrazu.

Zčervenání obrazu (populární při zranění v akčních hrách).

Blikající části obrazu.

Efekt tekoucí vody / příboje prolínáním několika blízkých modrých barev.

Změna atmosféry ze dne na noc (a naopak).

Abstrakce výřezu frame bufferu

O frame bufferu víme:

Ukazatel na levý horní pixel.

Šířku a výšku.

Výškový výřez umíme udělat - posuneme ukazatel o celé řádky a změníme výšku.

Šířkový výřez?

V paměti jsou řádky frame bufferu poskládané za sebe. Část chceme ignorovat. Přidáme nový údaj: stride – vzdálenost mezi začátky řádků v paměti.

Tedy pro výřez od 𝑥0 šířky 𝑤 posuneme ukazatel o 𝑥0, stride nastavíme na originální šířku řádku bufferu (resp. ta je stále stejná i při dalších operacích) a upravíme šířku a 𝑤.

typedef struct {
    Pixel * data;
    int width, height, stride;
} PixBuf;
Pixel * XY(PixBuf * pb, int x, int y) { return pb->data + x + y * pb->stride; }
Poznámka GRAFIT: Zdrojový fragment pracuje se stride v jednotkách Pixel, nikoli v bajtech. Neprovádí kontrolu souřadnic ani přetečení; jde o výukový fragment, ne bezpečný obecný přístup k obrazu.

Vykreslení obrázku do bufferu

Obrázek (sprite) reprezentujeme podobně jako výřez frame bufferu. Toto je výhodné, pokud chceme např. vykreslit část obrázku (protože máme např. uložený spritesheet).

Mám tedy zdrojový buffer a cílový buffer, oba stejné velikosti.

blitting - překopíruji obrázek pixel po pixelu (nebo celé řádky funkcí memcpy()).

Nevýhoda: nemám žádné škálování.

void blit(PixBuf * dst, PixBuf * src) {
    Pixel * d = dst->data, * s = src->data;
    for(int y = 0; y < src->height; y++) {
        memcpy(d, s, src->width * sizeof(Pixel));
        d += dst->stride; s += src->stride;
    }
}
Poznámka GRAFIT: Výukový fragment předpokládá platné stejně velké buffery, správný stride, dostatečnou cílovou paměť a nepřekrývající se kopírované oblasti. Pixel a hlavičky nejsou ve fragmentu definovány. Není to hotový projekt.

Vykreslení obrázku s maskou

masking - překopíruji jen některé pixely, vyhovující masce; typicky přeskakuji pixely s hodnotou 255 (0xFF) ve zdroji, čímž vzniká efekt průhledných částí obrázku.

Zde už logicky nemůžu použít memcpy().

Pomalejší než blitting kvůli vyhodnocování podmínky a podmíněným skokům navíc.

void blit_masked(PixBuf * dst, PixBuf * src) {
    Pixel * d = dst->data, * s = src->data;
    for(int y = 0; y < src->height; y++) {
        for(int x = 0; x < src->width; x++) {
            if(s[x] != 0xFF) d[x] = s[x]; // případně if(~s[x])
        }
        d += dst->stride; s += src->stride;
    }
}

Existují i jiné varianty maskování, ale uvedená na průhlednost je nejčastější.

Poznámka GRAFIT: Hodnota 0xFF zde označuje průhledný index v paletovém obrázku; pro libovolný RGB/RGBA formát to neplatí. Zkratka if(~s[x]) závisí na celočíselných promocích a typu Pixel, proto není obecnou náhradou porovnání s 0xFF.

Vykreslení obrázku s maskou a přebarvením

Vymezím v paletě část indexů pro přemapovatelné barvy (např. barva hráčovy frakce ve spritu).

Vytvořím pole pro mapování barev z jednoho indexu na druhý.

Použiju obdobný algoritmus jako pro masking.

void blit_masked_with_recolor(PixBuf * dst, PixBuf * src, Pixel * remap) {
    Pixel * d = dst->data, * s = src->data;
    for(int y = 0; y < src->height; y++) {
        for(int x = 0; x < src->width; x++) {
            if(s[x] != 0xFF) d[x] = remap[s[x]];
        }
        d += dst->stride; s += src->stride;
    }
}
Poznámka GRAFIT: Předpokládá se paletový index, úplná remapovací tabulka a platné buffery; bez kontroly rozsahů nejde o bezpečnou samostatnou implementaci.

Vykreslení úsečky

Z koncových bodů A, B s xA < xB určíme směrnici k. Při postupu v ose x přičítáme k k souřadnici y. Pro strmé úsečky zaměníme role os.

Úsečku ořízneme na obrazovku, řešíme přesnost směrnice a případně použijeme pevnou řádovou čárku. Tloušťku tato základní varianta neřeší.

Předloha uvádí použití při interpolaci i variantu pro kružnice. Důležité terminologické rozlišení je v poznámce GRAFIT níže.

Nativní rovnice podle zdroje

y=kx+q,k=yB−yAxB−xA,yi=yi−1+ky=kx+q,\qquad k=\frac{y_B-y_A}{x_B-x_A},\quad y_i=y_{i-1}+k
Poznámka GRAFIT: Popsaný přírůstek y += k odpovídá principu DDA s pevnou či plovoucí řádovou čárkou. Klasický celočíselný Bresenham rozhoduje podle kumulované chyby. Předloha je označuje společným názvem; původní znění zůstává v poznámkách/PDF.

Plný trojúhelník

Trojúhelník má horní vrchol s nejmenší 𝑦 souřadnicí a spodní vrchol s největší 𝑦 souřadnicí.

Zbylým vrcholem protáhnu vodorovnou dělící přímku; rozdělím trojúhelník na horní a spodní cíp.

Bressenhamovým algoritmem podle osy 𝑦 vedu z horního cípu dvě úsečky současně a vyplňuji části řádků mezi úsečkami.

Totéž udělám s dolním cípem; buď odspoda dvě nové úsečky, nebo odshora jednou úsečkou pokračuji a druhou interpoluji nově.

Varianty pro obdélníky, lichoběžníky od horního nebo spodního okraje obrazovky atd.

Algoritmus není dobře paralelizovatelný (řádky různě dlouhé); dnešní GPU rasterizují trojúhelníky jinak.

Textury, aneb opakované vzory a obrázky

Textura je pole pixelů (obvykle 2D, ale existují i jiná).

Typickým požadavkem je náhodný přístup na libovolné souřadnice.

A častým požadavkem je přístup na souřadnice mimo rozsah textury.

clamping – opakujeme krajní pixely (souřadnici ořízneme na rozsah textury).

wrapping – dláždíme texturou prostor (souřadnici modulíme velikostí textury).

Clamping je několik if-ů navíc, snažíme se jím na CPU šetřit.

Modulení jsou dva zbytky po dělení ((x % w + w) % w), což jsou dvě drahé operace.

Můžeme používat jen kladné souřadnice a jeden zbytek ušetřit.

Můžeme používat textury velikosti mocniny 2 a modulení realizovat bitovým ANDem.

Proto i v éře raných GPU existovaly jen POT (power-of-two) textury. NPOT textury se objevily později; dnes už je podporuje každá karta, ale ne se všemi schopnostmi. (Typicky neumí mip-mapping.)

Poznámka GRAFIT: Omezení NPOT závisí na API a verzi. Desktop OpenGL od 2.0 poskytuje plnou podporu NPOT včetně mipmap; starší OpenGL ES 2.0 / WebGL 1 mají omezení. Tvrzení PDF nelze přenášet na všechny dnešní GPU. Dokumentace Khronos

Texturovaný trojúhelník (2D)

Použijeme postup pro vykreslování plného trojúhelníku.

Místo vyplňování barvou budeme vyplňovat pixely z textury.

Každý vrchol trojúhelníku má s sebou i souřadnice na textuře (jen místo (𝑥, 𝑦) je označujeme (𝑢, 𝑣)).

Souřadnice (𝑢, 𝑣) interpolujeme Bressenhamovým algoritmem úplně stejně jako souřadnici 𝑥, tedy vedle 𝑘𝑥 musíme pro danou úsečku určit i 𝑘𝑢, 𝑘𝑣, vše vůči Δ𝑦.

Při vyplňování řádku interpolujeme Bressenhamovým algoritmem souřadnice (𝑢, 𝑣) mezi okraji řádku vůči Δ𝑥.

Interpolaci Bressenhamovým algoritmem lze využít i při vykreslování zvětšeného/zmenšeného obrázku.

Výpočet souřadnic

Lokální souřadnice v rámci objektu. (model space)

Transformace na globální souřadnice v prostoru. (world space)

Pro 3D prostor matice 𝑀 4×4 (homogenní souřadnice).

Nebo u starších her několik jednoduchých operací (posun apod.), případně jsou všechny souřadnice již globální.

Transformace na souřadnice z pohledu hráče (view space)

Pro 3D prostor maticí 𝑉 4×4.

Hráč je v počátku prostoru, svět je kolem něj vhodně otočen.

Dívá se dopředu v definované ose, typicke 𝑧.

Osa 𝑦 (obvykle) ukazuje nahoru, osa 𝑥 doprava.

U starších her obvykle jen jednoduchý posun a rotace/zkosení.

Perspektivní transformace

Komolý jehlan pohledu se mapuje do kvádru. Vzdálené objekty se v obraze sbližují; blízké se rozestupují.

Předloha používá reciprokou hloubku w = 1/z. Ve webovém doplňku ji přejmenováváme na q, aby se nepletla s homogenní souřadnicí w_c.

Zdroj dále probírá mapování blízké a vzdálené roviny a obrácenou osu hloubky pro změnu rozložení přesnosti. Konvence projekce musí být uvedena výslovně.

Doplněk GRAFIT: konvence a vysvětlení

q=1z,x′=xq,y′=yqq=\frac1z,\qquad x'=xq,\qquad y'=yq
Poznámka GRAFIT: Pro srozumitelnost zde značíme reciprokou hloubku q = 1/z, kterou předloha nazývá w. Nezaměňujte ji s homogenní složkou w_c v OpenGL. Po dělení clip souřadnic složkou w_c vznikají NDC, nikoli clip space. Dokumentace Khronos

Co s objekty mimo projekční frustum?

Můžu je nechat?

Objekty příliš daleko ve směru pohledu mě trápit nebudou.

Objekty před kamerou vlewo, dole, vpravo a nahoře budou mít velké souřadnice a nevlezou se do obrazu. Zbytečné procházení pixelů, které ve finále nebudu vykreslovat. Možná mi přetečou použité datové typy (pokud používám fixní řádovou čárku).

Objekty za kamerou se objeví před kamerou, ale středově převrácené.

Objekty po stranách (částečně vpředu a částečně vzadu) mohou být zdeformované zcela…

A objekty v rovině s kamerou (mající 𝑧= 0) způsobí dělení nulou.

Při tomto postupu chci ořezávat a musím ořezávat.

Ray casting a ray tracing

Obě staví na tom, že začínám s perspektivní projekcí a hledám obraz pro jednotlivé pixely.

ray tracing – vystřelím paprsek (ray) pro každý pixel na obrazovce.

Při velkém počtu pixelů velice pomalé a technicky náročné.

Souřadnice pro textury (𝑢, 𝑣) vynásobíme 𝑤.

Použijeme postup pro vykreslování texturovaného trojúhelníku, spolu s (𝑢𝑤, 𝑣𝑤) interpolujeme i 𝑤.

Textury na GPU

Textury se vykreslují různě zvětšované, při rasterizaci netrefujeme přesně jednotlivé texely, většinou trefujeme někam mezi.

Na CPU je nejlevnější vykreslit nejbližší texel (nearest).

Lze provádět lineární interpolaci (linear). To u 2D textury znamená 3 lerp-y na vykreslovaný fragment. Na CPU toto uměl původní Unreal engine.

Kvadratická interpolace vytváří hodnoty bodů mimo interpolovaný rozsah.

Textury se vykreslují i zmenšené. Z větší vzdálenosti vznikají jejich opakováním moaré.

Hodí se mít zmenšené verze textur.

Generují se tzv. mip mapy (mip mapping), tj. 2:1 zmenšeniny až do 1×1px.

Podle hustoty UV souřadnic při vykreslování fragmentu se určí i úroveň mip mapy.

Interpolace se potom provádí nejen mezi body v jedné úrovni mip mapy, ale i mezi dvěma sousedními úrovněmi mip mapy. (viz např. GL_LINEAR_MIPMAP_LINEAR)

Anizotropní filtrování – mipmapy nejen v ose 𝑢𝑣, ale také v jednotlivých osách.

NPOT textury nepodporují mip mapy.

Poznámka GRAFIT: NPOT mipmapping není obecně zakázán: závisí na API/verzi. Anizotropní filtr navíc lépe aproximuje protáhlou stopu pixelu v textuře; nevysvětluje jej pouze samostatná řada mipmap pro každou osu. Dokumentace Khronos

Hloubkový buffer, stencil buffer

Hloubkový buffer je speciální textura / frame buffer obsahující informaci o hloubce (souřadnice 𝑤) každého vykresleného bodu.

Stencil buffer umožňuje provádět maskovací operace při vykreslování (tedy vykreslit jen část, která není maskovaná stencil bufferem).

Vhodné např. pro efekt odrazů v zrcadle nebo v kalužích na cestě.

Nebo pro efekt portálů.

Zrcadlo chudého muže (bez stencil bufferu) – přezrcadlená geometrie součástí scény.

Poznámka GRAFIT: Hloubkový buffer ukládá transformovanou hloubkovou hodnotu po projekci a mapování, nikoli obecně samotné w či 1/z. Přesná vazba závisí na projekci a rozsahu hloubky. Dokumentace Khronos
